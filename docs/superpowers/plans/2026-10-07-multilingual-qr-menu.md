# Multilingual QR Menu Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use the `executing-plans` skill in inline mode to implement this plan task by task. Steps use checkbox syntax; stop at each checkpoint for review.

**Goal:** Add reviewed English and Simplified Chinese menu translations and a multilingual guest ordering flow while preserving Vietnamese as the canonical menu and staff language.

**Architecture:** Store translated dish fields on MenuItem and translated category names on Category, each with separate draft and approved values with a derived draft/approved/stale state. Generate drafts through a backend-only xKiro client using Qwen3.8 Max, expose drafts only through protected management routes, and let the guest UI resolve approved translations with Vietnamese fallback.

**Tech Stack:** Existing Express, TypeScript, Mongoose, React, Vite, Tailwind, native Node fetch, xKiro OpenAI-compatible Chat Completions API, Node test scripts, and Playwright.

**Path convention:** File paths are relative to the shared workspace root, which contains both QR_FOOD_ORDER_BE and QR_FOOD_ORDER_FE. Run package commands from the repository named in the step.

## Global Constraints

- Supported guest locales are exactly `vi`, `en`, and `zh-CN`; persisted translation keys are `en` and `zhCN`.
- Vietnamese remains canonical. Existing records without translations continue to work.
- The xKiro model ID defaults to `qwen/qwen3.8-max`; the API key exists only in the backend environment.
- No guest request invokes xKiro. Translation is generated by an authenticated owner/admin action and saved for review.
- Draft and stale translations are never returned by public menu/category reads.
- The order payload and staff/kitchen order item names remain Vietnamese.
- AI must not generate or modify ingredient, allergen, nutrition, or health claims.
- Add no model-specific SDK or i18n dependency; use existing fetch and local typed dictionaries.
- Tests use mocked xKiro responses. CI and local verification must not require a live xKiro key.
- Read the design before implementation: `docs/superpowers/specs/2026-10-07-multilingual-qr-menu-design.md`.

## Task 3: Add protected management APIs and safe public serialization

**Files:**
- Modify: `QR_FOOD_ORDER_BE/src/routes/menuRoutes.ts`
- Modify: `QR_FOOD_ORDER_BE/src/routes/categoryRoutes.ts`
- Create: `QR_FOOD_ORDER_BE/src/tests/menuTranslationRoutes.test.ts`
- Create: `QR_FOOD_ORDER_BE/src/tests/categoryTranslationRoutes.test.ts`
- Modify: `QR_FOOD_ORDER_BE/package.json`

**Interfaces:**
- `GET /api/menu/manage` and `GET /api/categories/manage` require owner/admin authentication, derive restaurant scope from the authenticated identity, and include all translation statuses. Do not accept or trust a client-supplied restaurant ID for these reads.
- `POST /api/menu/:id/translations/draft` and `POST /api/categories/:id/translations/draft` generate and persist draft values for both target locales while preserving any approved values.
- `PATCH /api/menu/:id/translations/:locale` accepts `{ name, description, publish }`; category equivalent accepts `{ name, publish }`. Save edits into draft; only `publish: true` promotes draft to approved.
- Management reads return each locale as `{ approved?, draft?, displayStatus }`. Public reads return plain locale text objects (`{ name, description }` for items and `{ name }` for categories) only when approved status is `APPROVED`; omit status/draft/stale fields.
- Translation routes scope records by the authenticated restaurant ID and accept only `en` or `zh-CN` in route parameters.
- Public GET routes return approved translations only.

- [ ] **Step 1: Write route tests before route code.** Cover unauthorized user, staff denial, wrong-restaurant item/category, draft generation, draft edit, publication, preservation of the prior approved value, and public draft/stale filtering.
- [ ] **Step 2: Add protected management GET routes before dynamic route matching.** Use `requireAuth` and `requireRole(["RESTAURANT_ADMIN"])`, which also admits owners under the existing auth helper; query only with the authenticated restaurant ID.
- [ ] **Step 3: Add draft generation and locale update routes.** Use the authenticated restaurant scope; validate the ID, locale, text lengths, and publish flag. Draft generation and edits preserve the prior approved value.
- [ ] **Step 4: Implement explicit promotion.** When `publish` is true, copy the edited draft into approved, mark it `APPROVED`, and clear the draft.
- [ ] **Step 5: Filter public responses and invalidate stale entries.** Public menu/category reads expose approved text only; Vietnamese source edits mark approved translations `STALE` and clear their drafts.
- [ ] **Step 6: Register focused route tests in `test:ci` and run them.** Confirm route tests use mocked xKiro generation and never require a live API key.
